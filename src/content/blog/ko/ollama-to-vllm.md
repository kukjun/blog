27–32B 오픈웨이트 모델 3개를 48GB GPU 2개 위에서 Ollama로 서빙하고 있었다. 배치
작업은 **90분**이 걸렸다. OpenAI 호환 게이트웨이 뒤에 vLLM으로 옮긴 뒤, 같은
작업이 **21분**에 끝났다 — 우리 하드웨어 기준 **처리량 4.8배**.

하지만 엔지니어링의 핵심은 그 숫자가 아니었다. 진짜 어려운 건 (1) 리더보드에서
제일 빠른 엔진이 아니라 *내가 운영할 수 있는* 엔진을 고르는 것, 그리고 (2) 양자화
모델이 프로덕션에서 믿을 만큼 여전히 맞는 답을 내는지 증명하는 것이었다.

## Ollama가 한계에 부딪힌 지점

Ollama는 우리를 빠르게 프로덕션까지 데려다줬다 — 그게 그 도구의 일이고, 잘 했다.
다만 실제 동시 부하에서 세 가지 구조적 이유로 천장을 쳤다.

- **Continuous batching 부재.** 요청이 순차 처리돼 GPU가 노는데도 요청은 줄 서서
  대기했다.
- **Tensor Parallelism 미지원.** NVLink로 묶인 GPU 2개인데, 한 모델이 둘에 걸치지
  못했다.
- **모델 전환 시 cold start.** 세 모델을 오갈 때마다 수십 초의 지연.

이건 버그가 아니라 설계 선택이다. Ollama는 "한 박스에서 모델을 쉽게 돌린다"에
최적화돼 있다. 우리는 그 형태를 넘어선 것뿐이다.

## 가장 빠른 엔진이 아니라, 믿을 수 있는 엔진

추론 서버 12개를 조사했다. 순수 처리량만 보면 선두는 분명했다.

| 엔진 | 처리량 (H100, 8B) | vLLM 대비 |
|---|---|---|
| SGLang | 16,215 tok/s | +29% |
| LMDeploy | 16,132 tok/s | +29% |
| **vLLM** | 12,553 tok/s | 기준 |
| llama.cpp | ~35 tok/s | ~−360× |

*(공개된 서드파티 벤치 수치, 내 측정 아님)*

vLLM은 **가장 빠르지 않았다.** 그래도 골랐다.

29%의 처리량 우위는 실재한다 — 하지만 새벽 2시에 엔진이 터졌을 때 참고할 답이 더
적은 엔진을 운영하는 비용도 실재한다. vLLM은 커뮤니티가 가장 크고 성숙했다. 해결된
이슈가 가장 많고, 검증된 엣지 케이스가 가장 많고, 레퍼런스 배포가 가장 많았다.
제품 앞단에 이걸 놓는 소규모 팀에겐 **운영 가능성이 최고 처리량을 이긴다.** 29%를
아끼려 더 빠르지만 얇은 엔진을 골랐다면, 일회성 속도 이득을 상시 운영 비용과 맞바꾼
셈이 됐을 것이다. 다시 해도 같게 판단한다.

## 진짜 비용: 양자화 모델이 여전히 맞는지 증명하기

이 마이그레이션의 실제 병목은 설정이 아니라 **검증**이었다.

Ollama에서 vLLM으로 간다는 건 GGUF(CPU 오프로드 최적화)에서 AWQ(GPU CUDA 커널
최적화)로 간다는 뜻이었다. 몇몇 모델은 공식 AWQ 빌드가 없어, 신뢰도를 알 수 없는
커뮤니티 변환본밖에 없었다. 양자화 포맷을 바꿔놓고 출력이 여전히 맞기를 *바랄* 수는
없다.

그래서 내부 벤치마크 세트를 만들었다. 같은 프롬프트를 기존 스택(GGUF)과 새 스택
(AWQ)에 통과시키고, 스왑을 신뢰하기 *전에* 출력 동등성을 비교했다. 내가 계속
돌아오게 되는 원칙: **일한 엔진이 자기 일을 스스로 인증하지 못한다** — 스왑이
안전한지는 별도의 검증자가 판정한다. 배포가 아니라 이 검증 단계에 대부분의 시간이
들어갔다.

재현을 위한 최종 실행 명령어:

```bash
uv run python -m vllm.entrypoints.openai.api_server \
    --model org/Model-32B-AWQ \
    --tensor-parallel-size 2 \
    --max-model-len 2048 \
    --max-num-seqs 16 \
    --gpu-memory-utilization 0.80 \
    --host 0.0.0.0 --port 8000
```

## 숫자 — 그리고 그게 실제로 의미하는 것

동일 32B급 모델, 동일 4bit 양자화, 동시 5개 요청, 3회 평균, 256토큰 생성.
**내부 벤치마크, 단일 하드웨어 구성** — 일반화된 주장이 아니다.

| 메트릭 | Ollama | vLLM | Δ |
|---|---|---|---|
| 동시 5개 완료 시간 | 38.9s | 5.7s | 6.8× |
| 평균 지연시간 | 23.31s | 6.48s | 3.6× |
| 요청당 처리량 | 15.0 tok/s | 40.6 tok/s | 2.7× |
| **총 처리량** | 98.6 tok/s | 472.5 tok/s | **4.8×** |

차이는 거의 전부 동시성에서 온다. Ollama는 순차 처리하고, vLLM은
**PagedAttention**(KV 캐시를 페이지 단위로 관리), **continuous batching**(요청이
실행 중인 배치에 동적으로 합류), **AWQ** 커널(역양자화를 행렬곱에 융합)로 작업을
겹친다. 이득의 정직한 모양을 보라: 헤드라인 4.8배는 *동시성 하의 처리량*이고,
단일 요청 지연은 3.6배로 더 완만하다. 페이지에서 제일 큰 숫자가 아니라, 워크로드에
맞는 메트릭을 보고해야 한다.

## 여러 모델 서빙: 하드와이어가 아니라 게이트웨이

모델 셋, 계약 하나. 앞단에 **OpenAI 호환 게이트웨이**(LiteLLM proxy)를 뒀다.

```
클라이언트 → 게이트웨이(인증) → ├─ vLLM A (GPU 0)  — 응답
                                ├─ vLLM B (GPU 1)  — 추론
                                └─ TEI  (CPU)      — 임베딩
```

클라이언트는 하나의 API(`/v1/chat/completions`)만 말한다. Ollama의 `/api/chat`을
OpenAI 호환 표면으로 바꾸자, 클라이언트 코드는 게이트웨이 뒤에 뭐가 도는지 신경
쓰지 않게 됐다 — 다음 엔진 교체는 클라이언트 재작성이 아니라 설정 한 줄이 된다.
**소유하는 건 인터페이스이고, 그 뒤 엔진은 교체 가능하다.** 이 분리는 어떤 단일
서빙 엔진보다 오래 간다 — 그게 핵심이다.

## 다른 엔지니어에게 해줄 말

1. **"충분히 좋고 빠르게"가 "완벽하게, 언젠가"를 이긴다.** 29% 빠른 엔진은 얇은
   안전망을 감수할 값이 아니었다.
2. **양자화 스왑은 설정 문제가 아니라 검증 문제다.** 배포 코드를 짜는 것보다 출력
   충실도를 증명하는 데 더 많은 시간을 잡아라.
3. **클라이언트와 엔진 사이에 인터페이스를 둬라.** 엔진은 *반드시* 바뀐다. 그걸
   클라이언트 마이그레이션으로 만들지 마라.

"그냥 LLM 엔진"처럼 보였다. 실제로는 LLM 옷을 입은 분산 시스템 최적화였다.
