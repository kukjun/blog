에이전트 제품에 사용자별 LLM 설정을 붙이는 작업을 했어요. 원래는 서버에 설정된
공용 백엔드로 요청을 보냈습니다. 여기에 개인 설정을 추가하면 각자 선택한 백엔드를
쓸 수 있을 거라고 생각하기 쉬워요. 그런데 저장 구조를 바꾸고 나서 호출부를 확인해보니,
실제로 요청을 보내는 쪽에는 예전 경로가 남아 있었습니다.

개인 설정을 찾지 못하면 서버의 공용 설정을 가져오는 코드였어요. 단일 설정으로
운영할 때는 기본값이었지만, 사용자가 비용을 나눠 부담하는 순간 의미가 달라집니다.
사용자에게는 개인 설정으로 실행하는 것처럼 보이는데, 요청은 다른 비용 주체로
넘어갈 수 있었습니다.

## 설정이 없다는 것과 공용을 선택했다는 건 달랐어요

문제를 작게 줄이면 이런 모양입니다. 아래 코드는 설명을 위해 새로 쓴 가상 예제이고,
당시 제품의 코드나 설정 이름이 아닙니다.

```javascript
const backend = personalSettings.get(userId) ?? sharedSettings;
```

값이 없을 때 기본값을 쓰는 평범한 코드예요. 하지만 여기서는 왼쪽과 오른쪽의 비용
주체가 달랐습니다. 개인 설정을 선택했는데 등록을 끝내지 못한 것과, 공용 설정을
선택한 것은 같은 상태가 아니었어요.

그래서 먼저 선택 범위를 정하고, 그 범위 안에서만 설정을 찾도록 했습니다. 공용을
선택하면 공용 설정을 쓰고, 개인을 선택하면 그 사용자의 설정만 찾습니다. 개인 설정이
없거나 잘못됐으면 실패를 반환해요. 설정 저장뿐 아니라 관리 권한과 비용 귀속도 이
선택에 연결했습니다.

저장소에서는 범위별로 활성 백엔드 하나만 허용하는 부분 유니크 인덱스를 사용했어요.
그건 같은 범위에 활성 설정 두 개가 생기는 문제를 막습니다. 호출부가 다른 범위로
넘어가는 문제까지 막아주는 것은 아니었어요. [부분 유니크 인덱스](https://www.postgresql.org/docs/current/indexes-partial.html)가
지키는 조건과 실행 코드가 지킬 조건을 나눠야 했습니다.

## 해석기를 고쳐도 호출부는 저절로 바뀌지 않았습니다

처음 변경에는 사용자별 범위를 해석하는 함수가 있었습니다. 그런데 실제 드라이버와
CLI 등의 호출부는 옛 환경변수 fallback을 계속 사용하고 있었어요. 저장 모델과 함수만
보고 완료라고 하면 놓치는 부분이었습니다.

기존 경로를 따라가며 범위 해석기를 호출부에 연결했습니다. 범위 검증을 거치지 않는
옛 함수를 외부에서 직접 가져다 쓸 수 있는 경로도 제한했어요. 같은 함수 이름으로
바꾸는 데서 끝내지 않고, 개인 설정이 없는 상태에서 실제 실행이 어디까지 진행되는지를
확인했습니다.

여기서 실패를 표현하는 방식은 화면마다 달랐습니다.

| 호출 표면 | 설정을 사용할 수 없을 때 |
|---|---|
| CLI와 드라이버 | 실행을 시작하기 전에 거부 |
| 운영 세션 | 설정을 고친 뒤 다시 진행할 수 있는 상태로 표시 |
| MCP 호출 | 설정 문제를 명시적인 실패로 반환 |

공통으로 지켜야 할 것은 하나였어요. 오류를 처리하는 동안 개인 요청이 공용 요청으로
바뀌면 안 됩니다. 다만 CLI 종료와 사용 중인 화면의 복구 안내를 똑같이 만들 필요는
없었습니다.

## 작은 예제에서는, 다른 범위를 조회할 이유부터 없앴어요

아래는 그 경계만 보여주는 실행 가능한 예제의 핵심입니다. 사용자 신원과 선택 범위는
인증된 사용자의 저장 설정에서 받는다는 전제예요. 모델이 만들어낸 도구 인자로
사용자나 비용 범위를 정하는 구조가 아닙니다.

```javascript
function resolveBackend(context, settings) {
  if (!['personal', 'shared'].includes(context.mode)) {
    throw failure('INVALID_SCOPE');
  }
  if (context.mode === 'personal' && !context.userId) {
    throw failure('MISSING_USER');
  }
  const scope = context.mode === 'personal'
    ? `personal/${context.userId}`
    : 'shared';
  const config = settings.get(scope);
  if (!config) throw failure('NOT_CONFIGURED');
  if (config.status !== 'ready') throw failure('INVALID_CONFIG');
  return { scope, backend: config.backend };
}

async function execute(context, settings, invoke) {
  const target = resolveBackend(context, settings);
  return invoke(target); // 실패해도 선택한 범위를 바꾸지 않아요.
}
```

설정은 선택한 키로 한 번 찾습니다. 그 뒤 호출이 rate limit으로 실패해도 공용 설정을
다시 조회하는 분기는 없습니다. 예제의 `status`는 검증 결과를 흉내 낸 값이고,
실제 자격증명 검증이나 과금 구현은 포함하지 않았어요.

[전체 예제와 검증 코드](/blog/examples/backend-scope.mjs)를 내려받아
`node backend-scope.mjs`로 실행할 수 있습니다. 네트워크 요청이나 API 키는 필요 없어요.
메모리 안의 가상 설정과 모의 호출만 사용합니다.

예제는 개인 설정의 미등록과 무효 상태에서는 호출 자체가 없고, 모의 HTTP 429에서는
선택한 개인 백엔드만 호출됐는지 확인합니다. 사용자 두 명의 설정이 섞이지 않는지,
설정을 고친 뒤 같은 개인 범위로 돌아오는지, 공용을 명시적으로 선택해야 공용 호출이
발생하는지도 검사해요. 이 검사는 글의 예제를 검증하는 것이고 제품 전체의 격리
보장을 대신하지는 않습니다.

## 실패를 잘 막았는데, 설정을 고쳐도 못 돌아왔어요

실제 사용자 경로를 검증하면서 다른 결함도 나왔습니다. 미등록과 무효 설정을 같은
사유로 표시하거나, 사용자가 설정을 수정했는데도 세션이 실패 상태에서 회복하지 못했어요.
다른 비용 주체로 요청이 새지 않는 것과 사용자가 다시 작업할 수 있는 것은 별개의
완료 조건이었습니다.

두 상태를 구별하고 재등록 후 세션이 회복하는 경로를 수정했습니다. OAuth 401에 대해서는
토큰을 강제로 갱신한 뒤 한 번 재시도하는 처리도 보완했어요. 재시도는 같은 사용자의
선택 범위에서 하는 것이고, 공용 백엔드로 전환하는 동작은 아니었습니다.

검증 범위는 구별해두려 합니다. 실제 경로 QA는 로컬 macOS와 SQLite 환경에서 수행했고,
설정 오류와 재등록 후 복구는 브라우저로 확인했습니다. OAuth 갱신 재시도는 의존성을
주입한 테스트로 검증했어요. 실제 구독 계정의 모든 성공과 갱신 상황, 컨테이너와
PostgreSQL을 포함한 모든 배포 환경까지 확인한 결과는 아닙니다. 위 가상 예제에도
OAuth 갱신은 넣지 않았어요.

처음에는 사용자별 설정을 어디에 저장할지가 큰 문제처럼 보였습니다. 작업을 마치고
나니 더 오래 남은 건 호출부에 남아 있던 기본값이었어요. 서버 하나가 쓰던 기본값을
여러 사용자가 나눠 쓰기 시작하면, 없는 값을 채우는 코드가 비용 주체를 바꾸는 코드가
될 수 있었습니다.

그래서 이 작업은 설정 추가만으로 끝낼 수 없었어요. 어떤 설정을 골랐는지, 실패했을 때
어디서 멈추는지, 사용자가 고친 뒤 어떻게 돌아오는지까지 이어서 확인해야 했습니다.
